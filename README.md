# 3xui_install

Установка VPN-сервера (3x-ui + Xray) на чистой Ubuntu 22/24.

## Актуальный скрипт — `3xui_install3.sh`

Схема без обратного прокси: панель сама держит защищённое соединение,
сертификат Let's Encrypt на голый IP и его продление делают штатные средства 3x-ui.

```bash
bash <(curl -Ls https://raw.githubusercontent.com/zhiharevds/3xui_install2/main/3xui_install3.sh)
```

Останавливать `unattended-upgrades` отдельно не нужно — скрипт делает это сам первым шагом.

Скрипт отказывается работать, если на сервере уже установлен x-ui: он сбрасывает
файрвол и пароль панели, поэтому запускать его можно только на чистой системе.

Настройки — переменными окружения перед запуском:

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `DEFAULT_EXIT` | `direct` | выход по умолчанию: `direct` или `warp` |
| `DISABLE_PING` | `0` | `1` — не отвечать на пинг. По умолчанию отвечает: так проще диагностировать, а скрытности почти не добавляет. На выбор сервера в mihomo не влияет |
| `DO_WARP` | `1` | ставить ли Cloudflare WARP. Ставится всегда, а **включается только там, где нужен** — см. «WARP: когда включается» ниже |
| `DO_UPGRADE` | `1` | обновлять ли систему перед установкой |
| `DO_SWAP` / `SWAP_MB` | `1` / как памяти | завести файл подкачки `/swapfile` (если свапа ещё нет и на диске хватает места), `swappiness 10`. Размер = объём памяти, округлённый до целых ГБ, от 1 до 4 ГБ; `SWAP_MB` задаёт свой. Страховка: без свапа при нехватке памяти система убивает Xray и туннель рвётся |
| `CREATE_INBOUNDS` | `1` | создавать ли подключения автоматически |
| `CLIENTS` | `Keenetic dzh` | список клиентов: шлюз и один для проверок. Устройства родных ходят домой через обратный туннель, отдельные клиенты им не нужны |
| `SERVER_NAME` | страна + конец адреса, напр. `GB-113` | имя сервера: так называются его узлы в панели шлюза и сервер в панели мониторинга |
| `SUB_PORT` | `2096` | порт подписок |
| `PORT_XHTTP` | `8080` | порт подключения XHTTP. Простого REALITY-TCP (vision) установщик больше не создаёт: провайдеры в России глушат его после ~5 соединений подряд — и мобильные, и домашний. **443 установщик не занимает** — он оставлен под синхронизацию папок (дверь Syncthing): его пускает почти любой прокси. Самопроверка в конце подтверждает, что 443 свободен |
| `DO_HY2` / `PORT_HY2` | `1` / `34443` | подключение Hysteria 2 (UDP). Клиенты — `<имя>-hy`; у `Keenetic-hy` своя подписка, остальным Hysteria добавляется в их общую |
| (при `DO_WARP=1` и `DO_HY2=1`) | всегда | запасной вход шлюза `Keenetic-hy-warp`: Hysteria, выход через Cloudflare WARP, своя подписка. Нужен, если адрес сервера Google считает российским. Заводится при любой установке, но в строку для шлюза попадает, только если WARP включён |
| (при `DO_WARP=1`) | всегда | сторож `warp-region-fix` (cron, раз в 10 минут): пока WARP включён и аккаунт Google или YouTube считает его выход российским, перерегистрирует WARP — сколько бы раз ни пришлось (у них разные базы: бывает аккаунт NL, а YouTube RU). Журнал `/var/log/warp-region.log`; посмотреть страну: `warp-region-fix --show` → «аккаунт/YouTube», например `NL/NL`; `--direct` — то же для самого адреса сервера, без WARP |
| `DO_MONITOR` | `1` | подключить сервер к домашней панели мониторинга VPS (см. ниже) |
| `MONITOR_KEY` | ключ домашнего шлюза | открытый ключ, которому разрешён запуск проверочного скрипта |
| `FORCE` | `0` | `1` — работать даже на непустом сервере |

### WARP: когда включается

Зачем он: Google может считать адрес сервера российским (сеть записана на владельца из РФ или Google
«выучил» адрес по людям за ним), а через WARP видит страну, где сервер стоит. Установщик меряет, как
Google и YouTube видят сам адрес сервера (`warp-region-fix --direct`), и решает:

| Случай | WARP |
|---|---|
| сервер в России | выключен: Cloudflare даёт выход WARP в той же стране — для Google всё равно Россия |
| Google и YouTube видят адрес нероссийским | выключен: WARP только замедлил бы |
| хоть один из них видит Россию | **включён**; сторож перерегистрирует его, пока выход не станет нероссийским |
| узнать не удалось | выключен; страну узла потом покажет панель мониторинга |
| `DEFAULT_EXIT=warp` | включён всегда |

Выключенный WARP остаётся установленным и зарегистрированным. Google со временем может передумать
(панель мониторинга пришлёт «узел: Google считает его российским») — тогда на сервере:

```bash
warp-on    # включить; напечатает строку для шлюза: sudo add-vps ИМЯ --warp "https://IP:2096/clash/<id-warp>"
warp-off   # выключить обратно
```

Строка для шлюза лежит и в `/root/warp-gateway-line.txt`.

### WARP на сервере, поставленном без WARP (`DO_WARP=0`)

Установщик на работающий сервер не запустить. Для WARP есть отдельный скрипт `warp-add.sh`:
он ставит то же, что шаг 6 установщика (WARP, сторож `warp-region-fix`, `warp-on`, `warp-off`),
заводит во входе Hysteria клиента, весь TCP которого выходит через WARP, и сразу включает WARP.

```bash
curl -fsSL https://raw.githubusercontent.com/zhiharevds/3xui_install2/main/warp-add.sh -o /root/warp-add.sh
bash /root/warp-add.sh                    # клиент Keenetic-hy-warp — вход для домашнего шлюза
bash /root/warp-add.sh HIP-NL-hy-warp     # сервер — выход каскада: клиент для входящего сервера (см. «Каскад»)
```

В конце скрипт печатает страну выхода WARP для Google («аккаунт/YouTube») и ссылку подписки нового
клиента. Для клиента `Keenetic-hy-warp` дальше — строка `sudo add-vps ИМЯ --warp "…"` на шлюзе (её
печатает `warp-on`). Памяти WARP берёт 300–400 МБ — на сервере с 1 ГБ нужен свап (команды ниже).
Повторный запуск ничего не ломает: что уже есть, скрипт пропускает.

Свап на уже работающем сервере (установщик туда не запустить) — ничего не перезапускает, размер = объём памяти:

```bash
swapon --show | grep -q . || { S=$(( ($(awk '/^MemTotal/{print int($2/1024)}' /proc/meminfo) + 1023) / 1024 )); fallocate -l ${S}G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile && echo '/swapfile none swap sw 0 0' >> /etc/fstab; }
echo 'vm.swappiness = 10' > /etc/sysctl.d/60-swap.conf && sysctl -p /etc/sysctl.d/60-swap.conf && free -m
```

## Панель мониторинга VPS — `vps-health.py`

Установщик кладёт на сервер `/usr/local/bin/vps-health.py` и прописывает в `authorized_keys`
ключ домашнего шлюза с ограничением `command=`: этим ключом можно ТОЛЬКО запустить проверочный
скрипт — зайти на сервер или пробросить порт нельзя. Скрипт ничего не меняет, только читает:
память, диск, службы, версию Xray, сроки сертификатов, подключения панели.

**`vps-health.py` в этом репозитории — единственная копия.** Панель мониторинга своей не держит.
Обновить скрипт на уже работающем сервере:

```bash
curl -fsSL https://raw.githubusercontent.com/zhiharevds/3xui_install2/main/vps-health.py -o /usr/local/bin/vps-health.py && chmod 755 /usr/local/bin/vps-health.py
```

## Подключение нового сервера к домашнему шлюзу (mihomo)

В конце установки скрипт печатает **одну строку** вида

```bash
sudo add-vps GB-113 "https://IP:2096/clash/<id>" "https://IP:2096/clash/<id-hysteria>" "https://IP:2096/clash/<id-warp>"
```

Её нужно выполнить **на шлюзе**. Команда сама допишет подписки в `/etc/mihomo/config.yaml`,
проверит конфиг, сохранит его в git и перечитает. В тумблеры сервер не попадает: трафик на него
пойдёт, только когда его впишут в автогруппу шлюза. Если в этот момент запущена игра,
конфиг не перечитывается (это сбило бы ей адреса) — после игры: `sudo add-vps --reload`.
Убрать сервер из шлюза: `sudo add-vps --remove GB-113`.
WARP-узел (третья ссылка) в строке есть, только если WARP на сервере включили. Включили позже —
`warp-on` напечатает строку `sudo add-vps GB-113 --warp "…"`: она добавит один этот узел.

Имя сервера — по правилу `ПРОВАЙДЕР-СТРАНА` (`HIP-NL`, `FORNEX-RU`): по нему в цепочке видно, через
какой сервер идёт трафик. Скрипт спрашивает его при запуске (или `SERVER_NAME=HIP-NL` перед запуском);
без ответа за минуту берёт «страна-конец адреса», например `GB-113`. Узлы на шлюзе `add-vps` называет
`ИМЯ-XHTTP`, `ИМЯ-HY2`, `ИМЯ-HY2-WARP` — только дефисы, без имени клиента.

`add-vps` — файл `add-vps.py` из этого репозитория; на шлюзе лежит как `/usr/local/bin/add-vps`.
Поставить или обновить:

```bash
sudo curl -fsSL https://raw.githubusercontent.com/zhiharevds/3xui_install2/main/add-vps.py -o /usr/local/bin/add-vps && sudo chmod 755 /usr/local/bin/add-vps
```

## Каскад: выход через второй сервер

Каскад — цепочка «шлюз → сервер-вход → сервер-выход → интернет». Нужен, когда до сервера-выхода
из дома не достучаться (из России режут его сеть), а со входа — можно. Сейчас так работают
`HIP-NL → ISH-DE` (узел шлюза `HIP-NL-HY2-DE`) и `HIP-NL → ISH-UK` (узел `HIP-NL-HY2-UK`, только для
ChatGPT: клиенты `HIP-NL-hy` на ISH-UK и `Keenetic-hy-uk` на HIP-NL, исходящий `ish-uk-hy2`). Обе части — Hysteria.
Выход каскада ставится установщиком как обычный сервер, но с `DO_HOME=0`: вход домой через него из России не дойдёт.

Если Hysteria на участке вход→выход режут (так с Москвы до Лондона), второй участок делается по XHTTP:
на выходе — клиент vless во входе XHTTP, на входе — исходящий `vless` с `network: xhttp`, REALITY
(SNI, `publicKey`, `shortId` — из подписки выхода `/clash/`) и отпечатком `chrome` (Xray 26.9.8+ на выходе
без него не пустит). Так работает `FORNEX-RU → ISH-UK`: узел шлюза `FORNEX-RU-HY2-UK`, исходящий
`ish-uk-xhttp`. Проверить участок до настройки — временным Xray на входе (`xray run -c` с socks на
127.0.0.1 и этим исходящим, через `timeout`), скачать через него 50 МБ несколько раз.

SNI для REALITY менять только после сравнения: два временных клиента со старым и новым SNI
(на выходе на время оба имени в `serverNames`), по очереди по 30 МБ. 28.10.2026 на участке
Москва → Лондон сосед из той же подсети (`mail.hostlayerspider.com`, найден `RealiTLScanner`)
дал ~0,1 Мбит/с, а `api.twitch.tv` — 180 Мбит/с.

Проверить, режут ли сервер из дома: на шлюзе скачать с панели сервера файл больше 16 КБ, например
`curl -sk -o /dev/null -w "%{size_download}\n" https://IP:ПОРТ/ПУТЬ/assets/<любой .js со страницы входа>`.
Обрыв на ~20 КБ — режут, нужен каскад.

```
шлюз ──Hysteria──▶ HIP-NL ──Hysteria──▶ ISH-DE ──▶ интернет
      клиент Keenetic-hy-de     клиент HIP-NL-hy
      (подписка HIP-NL)         (исходящий ish-de-hy2 на HIP-NL)
```

`add-vps` каскады не умеет — всё делается руками в трёх местах:

1. **Сервер-выход (ISH-DE).** Во вход Hysteria — клиент по имени входящего сервера (`HIP-NL-hy`).
   Нужны его `auth`, пароль маскировки salamander входа и адрес/порт сервера.
2. **Сервер-вход (HIP-NL).** В шаблоне Xray панели — исходящий `hysteria` (адрес и порт выхода,
   `auth` из шага 1, `salamander` с тем же паролем, `alpn: h3`, тег `ish-de-hy2`). Во вход Hysteria —
   клиент `Keenetic-hy-de` со своей подпиской. Правило шаблона `user: [Keenetic-hy-de] → ish-de-hy2`
   ставится сразу за правилом `geoip:private` (выше правила «российское — напрямую»: иначе российские
   сайты ушли бы с HIP-NL). После правки шаблона — перезапустить Xray.
3. **Шлюз.** В `/etc/mihomo/config.yaml` — подписка (`proxy-providers`) на клиента из шага 2 с именем
   узла по правилу `ВХОД-HY2-ВЫХОД` (`HIP-NL-HY2-DE`), как блок `hip-nl-hy2-de`; узел — в нужную
   автогруппу. Проверка `mihomo -t`, перечитать (`add-vps --reload`), коммит в git шлюза.

**WARP на выходе каскада** — когда Google считает адрес сервера-выхода российским:

1. На сервере-выходе: `bash /root/warp-add.sh HIP-NL-hy-warp` (раздел «WARP на сервере, поставленном
   без WARP»). Скрипт напечатает страну выхода WARP. Клиент `HIP-NL-hy-warp` выходит через WARP.
2. На сервере-входе — второй исходящий, копия первого с `auth` клиента `HIP-NL-hy-warp` и тегом
   `ish-de-hy2-warp`; клиент `Keenetic-hy-de-warp` и правило `user: [Keenetic-hy-de-warp] → ish-de-hy2-warp`
   рядом с правилом из шага 2.
3. На шлюзе — подписка на `Keenetic-hy-de-warp`, узел `HIP-NL-HY2-DE-WARP`, в группу «🌍 VPS для Google».

## Вход «устройство вне дома → домашний шлюз»

Телефоны и компьютеры вне дома выходят в интернет через домашний шлюз и живут по домашним правилам
и тумблерам. Белый адрес дома не нужен: шлюз сам держит обратный туннель к серверу, а сервер лишь
пересылает в него всё, что пришло на «дверь» (порт 2053, TCP и UDP) — содержимого он не видит.

Установщик делает серверную половину сам (`DO_HOME=1`, скрипт `home-pipe.py`): входы `HOME-PIPE-HY`
(58932/udp), `HOME-PIPE-TCP` (58930) и `HOME-DOOR` (2053) в панели, правило маршрута и порты в файрволе.
В итоговой строке `add-vps` появляется хвост `--pipe <строка>` — шлюз по нему подключается к серверу,
и у всех устройств на странице «Подключение устройств» панели мониторинга появляется ещё один вход.

- Уже стоящий сервер: `python3 home-pipe.py --name ИМЯ --password ПАРОЛЬ_ADMIN`, затем на шлюзе
  `sudo add-vps ИМЯ --pipe <строка>`.
- После правки входов `HOME-*` в панели мышкой — «Перезапустить Xray», иначе вход домой замолчит.
- Ключи людей живут на шлюзе (команда `phones`, файл `phones.py`), в панели сервера их нет.
- На шлюзе нужны служба `home-pipe` (Xray 26.9.9+) и входы mihomo `phones-*`.

Почему так. Новое ядро Xray (26.9.8+, панель 3.8+) отвергает приветствие REALITY без
пост-квантового ключа X25519MLKEM768, а обычная ссылка `vless://` этот флаг не несёт. Поэтому
скрипт включает подписку в родном формате mihomo (`https://IP:2096/clash/<id>`): в ней панель сама
ставит `support-x25519mlkem768: true` и отпечаток `chrome` (у `firefox` в mihomo этого ключа нет —
подключения создаются с `chrome`). Проверено 2026-09-17 на чистой Ubuntu 24.04, панель 3.8.5,
Xray 26.9.9, mihomo 1.19.30: по такой подписке XHTTP (REALITY) работает без поправок; по обычной
`/sub/` — отказ «REALITY authentication failed». Самопроверка в конце установки это проверяет.

Телефонам и программам на ядре Xray (v2rayNG, Streisand и т.п.) хватает обычной подписки `/sub/`.
Hysteria это не касается: она не REALITY.

## Старый скрипт — `3xui_install2.sh`

Оставлен для истории. Ставил дополнительно Caddy как обратный прокси и требовал
ручных доделок: прописать сертификат панели, добавить перезапуск панели в хук
продления, задать «мин. версию клиента» для mihomo. В третьей версии всё это
делается само.
